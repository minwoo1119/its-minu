  - 스케일바 캘리브레이션 및 형상 정량 분석 대시보드
    현미경 스케일바를 픽셀 단위로 보정하여 실제 물리 단위(μm, nm)로 면적, Feret 직경, 원형도(Circularity)를 자동 산출하고 분포 차트 및 통계 테이블로 시각화합니다.
  - 미세 입자 전처리 및 분석 조건 설정

• 프로젝트 개요 (Overview):

• 문제 정의 및 배경 (Problem Statement):
  산업용 아날로그/디지털 계측 장비의 수치를 자동 로깅하기 위해 카메라로 7-Segment LED 화면을 촬영할 때, 교류 전원 주파수에 의한 LED 플리커(Flicker) 현상과 주변 조명 반사로 인해 일반적인 OCR이 특정 프레임에서 숫자를 심각하게 오인식하는 문제가 있었습니다. 30 FPS 실시간 비디오 스트림에서 플리커 노이즈를 시간축으로 보정하고 수치를 안정적으로 인식하는 시스템이 필요했습니다.

• 핵심 제약 조건 (Constraints):
  - [실시간 비디오 프레임] 카메라 영상 입력 기준 30 FPS (33ms 이내) 프레임 드롭 없는 고속 연속 추론
  - [LED 플리커 제약] 카메라 셔터 스피드와 LED 구동 주파수 차이로 발생하는 세그먼트 소실 방어
  - [경량 엣지 하드웨어] 고가 외장 GPU 없이 일반 산업용 PC CPU 환경에서 안정적 구동

• 시스템 아키텍처 및 처리 파이프라인 (Architecture Steps):
  01. Dynamic ROI Selection
     설명: 사용자 지정 또는 자동 템플릿 매칭을 통한 7-Segment 디스플레이 영역 크롭
  02. Contrast & Adaptive Binarization
     설명: LED 세그먼트 발광 대비를 강조하고 외부 조명 반사를 차단하는 적응형 이진화
  03. LightSVTR ONNX Inference
     설명: 경량 트랜스포머 기반 LightSVTR 모델의 ONNX Runtime CPU 고속 추론
  04. Time-Series Continuity Calibration
     설명: 슬라이딩 윈도우 신뢰도 가중치 기반 인접 프레임 시간축 이상치 필터링 및 복원

• 기술 스택 및 선정이유 (Tech Choices & Reasons):
  - LightSVTR + ONNX Runtime: 경량 텍스트 인식 트랜스포머 모델을 ONNX Runtime으로 구동하여 CPU 환경에서도 30fps 영상 처리를 보장했습니다.
  - Time-Series Calibration Filter: LED 디스플레이의 주기적인 플리커로 인한 순간적 오인식을 인접 프레임 간 연속성 검증으로 완벽히 제거했습니다.
  - Clean Architecture & Factory Pattern: 추후 다른 OCR 모델이나 비전 알고리즘으로 손쉽게 교체할 수 있도록 도메인/인프라/UI 계층을 분리했습니다.

• 주요 핵심 기능 (Key Features):
  - 동적 ROI 설정 및 실시간 프레임 스트리밍
    카메라 및 비디오 입력에서 관심 영역(ROI)을 드래그하여 지정하고 즉시 추론을 개시하는 사용자 친화적 UI를 제공합니다.
  - 시간축 이상치 필터링 및 복원

  - 해결 방법: 단일 프레임 판단 대신 최근 5개 프레임의 소프트맥스 확률 분포를 누적하여 종합 판정하는 시간축 누적 디코딩을 설계했습니다.
  - 결과/성과: 플리커로 인한 누락 프레임이 발생해도 100% 온전한 숫자 시퀀스를 안정적으로 복원했습니다.

  - Turborepo & pnpm Workspace: 모바일 앱, 백엔드 API, 공통 TypeScript 타입, GIS 데이터 빌드 스크립트를 단일 저장소에서 효율적으로 공유·확장하기 위해 구성했습니다.

• 프로젝트 개요 (Overview):
  사내 규정, 계약서, 특허 등 민감 문서가 외부 클라우드 API로 전송되는 데이터 유출 리스크와 종량제 비용을 원천 차단하기 위해 구축한 오픈소스 데스크톱-웹 하이브리드 RAG(Retrieval-Augmented Generation) 플랫폼입니다. 외부 전송 데이터 0 바이트(Zero Data Egress) 원칙 하에 Ollama(Qwen2.5-7B) 로컬 LLM과 BAAI/bge-m3 온디바이스 임베딩을 100% 자립 구동합니다. Windows Tkinter 기반 원클릭 데스크톱 런처를 통해 비개발자도 인프라·서버·UI를 즉시 가동할 수 있으며, Docker 가동 시 컨테이너(PostgreSQL 16, Qdrant HNSW, MinIO S3) 모드로, Docker 미가동 시 SQLite + In-Memory Qdrant + 로컬 디렉터리 스토리지로 무중단 자동 폴백되는 하이브리드 영속성 계층을 제공합니다. 교보 디자인 시스템(KDS) 기반의 정갈한 2열 작업대, 답변 내 [파일명, p.숫자] 상호작용 인라인 인용 배지, 검색 점수·원본 프롬프트·소요시간(ms)을 투명하게 감사할 수 있는 TraceDrawer를 단독 설계 및 구현했습니다.

• 기술 스택 및 선정이유 (Tech Choices & Reasons):
  - Desktop Launcher (Python / Tkinter & Velopack): 개발 도구(Docker, Node, Python CLI)를 직접 다루지 못하는 사내 실무자도 인스톨러 더블클릭 한 번으로 즉시 사내 문서 질의응답을 시작할 수 있도록 Windows KDS 테마 데스크톱 런처를 구현하고, 64KB 파이프 버퍼 데드락 방지 비동기 로그 리더 및 Velopack 원클릭 설치/포터블 패키징을 적용했습니다.
  - Next.js 14 (App Router) & Tailwind CSS: 장시간 문서 판독 피로도를 낮추기 위해 교보 디자인 시스템(KDS) 시각 원칙(이모지 배제, 1px 정갈한 헤어라인, 차분한 Indigo 테마)을 준수한 Reading-First 2열 단일 사용자 작업대를 구현하고, 클릭 가능한 [파일명, p.숫자] 상호작용 인용 배지와 TraceDrawer를 제공하기 위해 채택했습니다.
  - FastAPI 0.115 Async & Python Protocol Clean Architecture: 특정 프레임워크(LangChain 등) 종속 없이 Python Protocol 기반으로 LLM 및 임베딩 어댑터를 추상화하여 도메인 독립성을 확보하고, 문서 수집·청킹·벡터 검색·스트리밍 생성 전 과정을 비동기(AsyncIO) 논블로킹으로 처리하기 위해 채택했습니다.
  - Hybrid Persistence (Docker Compose / SQLite & In-Memory Qdrant): Docker Desktop 가동 시 컨테이너 인프라(PostgreSQL 16, Qdrant HNSW, MinIO S3)로 연결되고, Docker 미가동 시에도 SQLite, 인메모리 Qdrant, 로컬 디스크 파일 스토리지로 100% 무중단 자동 폴백되는 환경 적응형 하이브리드 영속성 계층을 구현하기 위해 채택했습니다.
  - Local Ollama (Qwen2.5-7B) & BAAI/bge-m3 (1024-dim): 외부 전송 데이터량 0 바이트(Zero Data Egress)를 보장하기 위해 한국어 의미 밀집도가 높은 온디바이스 BGE-M3 임베딩과 로컬 GPU에서 완전 자립 구동되는 Qwen2.5-7B 모델 및 추론 어댑터를 설계했습니다.
  - Pytest (59 Automated Tests, 100% Pass): 워크스페이스 격리, 문서 수집, 벡터 검색, 어댑터 폴백 등 핵심 엔터프라이즈 RAG 로직의 안정성을 보증하기 위해 apps/api 기준 59건의 자동화 테스트를 전건 통과 검증했습니다.

• 주요 핵심 기능 (Key Features):
  - 원클릭 데스크톱 런처 (Zero Setup Barrier)
    개발 도구(Docker, Node.js, Python CLI)를 다루지 못하는 사내 실무자도 인스톨러 더블클릭 한 번으로 백엔드, 프론트엔드, 영속성 계층을 자동 일괄 기동할 수 있습니다. 64KB 파이프 버퍼 데드락을 방지하는 비동기 UTF-8 로그 리더 스레드, 소켓 바인딩(is_port_open) 기반 1초 초고속 헬스체크, 브라우저 자동 오픈, 런처 종료 시 taskkill /F /T 기반 자식/손자 프로세스 완전 정리를 보장하며, Velopack 기반 원클릭 인스톨러(dograc-win-Setup.exe ~53MB) 및 무설치본(Portable.zip ~46MB) 패키징을 완비했습니다.
  - 투명한 실행 추적 및 감사 (Transparency First - TraceDrawer)
    검색(Retrieval)과 생성(Generation)을 단일 블랙박스로 감추지 않고 명확히 분리 기록합니다. 각 답변마다 실행 분석(Trace) 서랍을 열어 추출된 청크들의 코사인 유사도 점수, 매칭 본문, 전체 지연시간(ms), LLM에 실제 주입된 프롬프트 전문을 전수 감사(Audit)할 수 있어 검색 실패(문서 미발견)와 생성 실패(환각)를 명확히 구분하고 디버깅할 수 있습니다.
  - 신뢰 기반 근거 인용 배지 (Grounded Citations) & 엄격한 환각 거절
    AI 답변의 모든 문장에 참조 문서 위치([파일명, p.숫자])를 인식하여 클릭 가능한 상호작용 배지로 렌더링합니다. 사용자는 배지를 클릭하여 원문 발췌문과 페이지를 즉시 대조할 수 있으며, 문서에 없는 내용에 대해서는 거짓 답변(환각)을 지어내지 않고 정직하게 답변 불가를 안내하는 엄격한 거절 지침(Refusal Constraint)을 확립했습니다.
  - 환경 적응형 하이브리드 영속성 계층 (Dual Storage Auto-Fallback)
    Docker Desktop 실행 상태를 스스로 감지하여, Docker 가동 시 컨테이너 인프라(PostgreSQL 16 메타데이터/Trace, Qdrant HNSW 인덱스, MinIO S3 문서 불변 보관)로 자동 연결되고, Docker 미가동 시에도 시스템 중단 없이 SQLite(dograc_local.db) + 인메모리 Qdrant(:memory:) + 로컬 디렉터리 스토리지(data/storage/)로 100% 무중단 자동 전환됩니다.
  - PyMuPDF 정밀 파싱 & 이중 보안 인가 (Dual Authorization)
    PyMuPDF 기반 정밀 페이지 텍스트 추출 및 단락(

) 경계를 보존하는 재귀적 문자 청킹(800자 청크, 120자 오버랩), BGE-M3(1024차원) 임베딩을 지원합니다. 또한 Qdrant 벡터 검색 후 관계형 DB(PostgreSQL/SQLite)에서 워크스페이스 소유권 및 문서 ready 상태를 관계형 조인으로 재검증하는 이중 보안 인가(Dual Authorization)를 통해 완벽한 데이터 격리를 보장합니다.
  - Reading-First KDS 웹 인터페이스 & 즉시 작업대 진입
    교보 디자인 시스템(KDS) 시각 원칙(이모지 배제, 1px 정갈한 헤어라인, 차분한 Indigo 테마)을 준수하여 장시간 문서 판독에 최적화했습니다. 불필요한 로그인/회원가입 절차를 걷어내고 접속 즉시 문서 보관함과 채팅 패널을 활용할 수 있는 2열 단일 사용자 작업대를 제공합니다.

• 트러블슈팅 및 기술적 난제 해결 (Troubleshooting):
  [이슈 1]
  - 문제 상황: 데스크톱 런처에서 서브프로세스 기동 시 Windows 파이프 버퍼 용량(64KB) 초과로 프로세스가 멈추는 데드락 현상과, 런처 종료 시 백엔드/프론트엔드가 백그라운드에 남아 포트를 점유하는 고아 프로세스 문제가 발생했습니다.
  - 해결 방법: 비동기 UTF-8 로그 리더 스레드를 적용하여 실시간 스트림 버퍼 비우기를 구현하고, 소켓 바인딩(is_port_open) 기반 1초 초고속 헬스체크를 도입했습니다. 런처 종료 시에는 taskkill /F /T로 자식 및 손자 프로세스 트리를 일괄 강제 종료하도록 생명주기를 오케스트레이션했습니다.
  - 결과/성과: 버퍼 오버플로우에 의한 기동 데드락을 원천 차단(0건)하고, 런처 종료 시 잔여 고아 프로세스가 100% 깨끗이 정리되는 안정적인 데스크톱 라이프사이클을 완성했습니다.
  [이슈 2]
  - 문제 상황: 사내 규정 및 기밀 문서를 다루는 환경에서 상용 클라우드 API 호출 시 외부 유출 위험과 종량제 비용이 발생하며, 문맥에 없는 내용에 대해 LLM이 허위 사실을 지어내거나 출처 페이지를 왜곡하는 환각(Hallucination)이 발생했습니다.
  - 해결 방법: 외부 전송 데이터량 0 바이트 원칙 하에 Ollama(Qwen2.5-7B) 로컬 모델과 BGE-M3 온디바이스 임베딩을 100% 로컬 GPU에서 구동했습니다. 시스템 프롬프트에 엄격한 거절 지침(Refusal Constraint)과 정규화된 Few-shot을 주입하고, [파일명, p.숫자] 문법을 정규화하여 프론트엔드 인터랙티브 인용 배지와 1:1로 결합했습니다.
  - 결과/성과: 외부 네트워크 통신 없는 완벽한 사내 데이터 주권을 확립하고, 근거 없는 답변 생성률을 0%로 통제하며 모든 생성 문장에 대해 실제 문서 페이지와 일치하는 정밀한 원문 앵커링을 달성했습니다.

  - 문제 상황: Docker Desktop이 설치되지 않았거나 실행되지 않은 실무자 단말기에서는 PostgreSQL, Qdrant, MinIO 컨테이너를 구동할 수 없어 서비스 진입 장벽이 극도로 높아지는 문제가 있었습니다.
  - 해결 방법: 백엔드 기동 시 Docker 상태를 실시간 진단하여, 가동 중이면 컨테이너 인프라로 자동 연결하고 미가동 시 시스템 중단 없이 SQLite(dograc_local.db) + 인메모리 Qdrant(:memory:) + 로컬 디렉터리 스토리지(data/storage/)로 100% 자동 폴백 전환되는 환경 적응형 하이브리드 영속성 엔진(main.py)을 구축했습니다.

• 배운 점 및 인사이트 (Lessons Learned):
  - RAG 파이프라인의 핵심은 단순히 거대한 LLM을 붙이는 것이 아니라, 검색(Retrieval)과 생성(Generation)을 단일 블랙박스로 감추지 않고 분리 감사(Trace)할 수 있는 투명성과, 사내 보안을 완벽히 지키는 데이터 주권(Zero Data Egress)에 있음을 체득했습니다.
  - 기업 실무 환경에서는 화려한 기능보다 비개발자도 더블클릭 한 번으로 구동 가능한 Zero Setup Barrier와, "정직하게 모른다고 답하고 아는 것은 원문 페이지를 명확히 짚어주는 신뢰성(Grounded Citations)"이 제품의 성패를 가른다는 것을 실감했습니다.

• 한계점 (Limitations):
  - 현재는 PDF 포맷을 중심으로 색인 파이프라인이 최적화되어 있어, 사내 주요 문서 포맷(DOCX, PPTX, Markdown)의 추가 파서 확장이 요구됩니다.
  - 고밀도 벡터 검색(Dense Retrieval) 중심 구조로 특정 고유명사나 모델명, 부품 번호 검색 시 키워드 매칭 보완(Hybrid Search)이 요구됩니다.

• 향후 개선 계획 (Next Steps):
  - [검색 품질 고도화 (Phase 2)] DOCX, PPTX, Markdown 등 사내 주요 문서 포맷 파서 확장, BM25 키워드 검색 + BGE-M3 밀집 벡터 하이브리드 검색(RRF 순위 융합), Cross-Encoder Reranker 도입으로 상위 랭킹 정확도를 극대화할 계획입니다.
  - [도메인 파인튜닝 파이프라인 (Phase 3)] Trace 감사 로그 및 RAG 평가 골든 데이터셋 기반 LoRA / QLoRA 모델 튜닝 파이프라인을 자동화하여, 사내 도메인 근거 인용 준수율 및 답변 거절 정확도 행동을 지속 교정할 예정입니다.

  - [컴퓨팅 및 전력] NVIDIA Jetson Orin Nano 8GB, 15W 저전력 임베디드 엣지 보드 환경
  - [지연시간 & 처리량] 제조 라인 실시간 검사를 위한 30 FPS 이상 (33ms 이하) 인라인 판정
  - [정확도 손실 한계] 양자화(Quantization) 시 이상치 검출 AUROC 정확도 손실 0.5%p 미만 유지
  - [비지도 학습] 불량 이미지 없이 정상 제품 이미지만으로 이상치 판정 기준 자동 수립

• 시스템 아키텍처 및 처리 파이프라인 (Architecture Steps):
  01. Patch Feature Extraction
     설명: 정상 제품 이미지로부터 WideResNet 중간 레이어 패치 특징 맵 추출
  02. CoreSet Subsampling
     설명: 메모리 뱅크 10% 희소 샘플링을 통해 k-NN 최근접 탐색 연산량 90% 축소
  03. ONNX Export & INT8 Calibration
     설명: 대표 데이터셋 캘리브레이션을 통한 FP16 / INT8 고속 추론 엔진 빌드
  04. C++ Inference Runtime on Jetson
     설명: Python GIL 오버헤드 없는 C++ 네이티브 실행 및 히트맵 이상치 산출

• 기술 스택 및 선정이유 (Tech Choices & Reasons):
  - PatchCore Algorithm: 결함 데이터 없이 정상 샘플만으로 높은 결함 국소화(Localization) 성능을 발휘하여 산업용 제조 라인 콜드 스타트에 최적이기 때문에 채택했습니다.
  - TensorRT FP16 & INT8 Quantization: 제한된 엣지 연산 자원(15W)에서 메모리 대역폭 한계를 극복하고 4.8배 이상의 속도 향상을 얻기 위해 적용했습니다.
  - C++ Inference Runtime: Python의 인터프리터 오버헤드와 GIL을 배제하고 실시간 카메라 입력과 직결되는 저지연 런타임을 구성하기 위해 선택했습니다.

• 주요 핵심 기능 (Key Features):
  - 정상 데이터 기반 비지도 이상 탐지 파이프라인
    불량 샘플이 없는 상태에서도 정상 제품 이미지 패치 특징 맵을 메모리 뱅크로 구축하여 미세 스크래치, 이물, 균열을 자동 검출합니다.
  - CoreSet 메모리 뱅크 90% 압축
    탐욕적 CoreSet 샘플링 알고리즘을 적용하여 메모리 뱅크 크기를 10%로 줄이면서도 결함 검출 AUROC 손실을 최소화했습니다.
  - Jetson Orin Nano C++ 실시간 70 FPS 서빙
    TensorRT C++ API와 GStreamer 파이프라인을 연동하여 14.3ms 내에 히트맵을 생성하고 불량을 판정하는 엣지 서빙 환경을 완성했습니다.

  - PatchCore 모델 학습 및 MVTec AD 데이터셋 기반 벤치마크 환경 구축
  - 메모리 뱅크 CoreSet 최적화 및 k-NN 최근접 이웃 탐색 연산 병목 해결
  - PyTorch → ONNX 그래프 변환 및 TensorRT INT8 캘리브레이션 프로파일러 작성
  - Jetson Orin Nano 타겟 C++ 런타임 구현 및 FP32/FP16/INT8 정밀도별 레이턴시/메모리 측정

• 트러블슈팅 및 기술적 난제 해결 (Troubleshooting):
  [이슈 1]
  - 문제 상황: INT8 양자화 시 메모리 뱅크 거리 계산 과정에서 오버플로우 및 미세 결함에 대한 이상치 점수 왜곡이 발생했습니다.
  - 해결 방법: 백본 피처 맵 레이어만 INT8로 양자화하고 k-NN 거리 계산 레이어는 FP16 혼합 정밀도(Mixed Precision)를 유지하도록 레이어별 정밀도를 매핑했습니다.
  - 결과/성과: FP32 대비 AUROC 손실을 0.2%p 이내로 완벽히 방어하면서 14.3ms의 압도적인 추론 속도를 확보했습니다.

• 성능 최적화 전후 비교 (Performance Comparisons):
  - [추론 지연 시간 (Latency)] 변경 전: PyTorch FP32: 128.5 ms → 변경 후: TensorRT INT8: 14.3 ms (개선도: -88.9% (약 9배 단축))
  - [처리량 (Throughput)] 변경 전: 7.8 FPS (실시간 불가) → 변경 후: 69.9 FPS (초고속 실시간) (개선도: +796% 향상)
  - [메모리 점유율 (VRAM)] 변경 전: 1,420 MB → 변경 후: 420 MB (개선도: -70.4% 절감)
  - [이상치 탐지 정확도 (AUROC)] 변경 전: FP32: 99.2% → 변경 후: INT8: 99.0% (개선도: 정확도 손실 0.2%p 불과)

• 정량적 성과 지표 (Result Metrics):
  - [추론 지연 시간] 14.3 ms (69.9 FPS) : Jetson Orin Nano 15W 저전력 보드 실시간 인라인 검사 달성
  - [속도 가속률] 4.8배 가속 : PyTorch FP32 baseline 대비 압도적 처리량 향상
  - [이상치 탐지율] 99.0% AUROC : INT8 양자화 후에도 결함 검출 정확도 손실 0.2%p 이내 방어

• 배운 점 및 인사이트 (Lessons Learned):
  - 엣지 디바이스에서의 딥러닝 서빙은 단순히 모델을 작게 만드는 것을 넘어, 타겟 하드웨어의 메모리 대역폭과 텐서 코어 특성에 맞춘 양자화 캘리브레이션이 결정적인 차이를 만든다는 것을 배웠습니다.
  - C++ 런타임으로의 전환을 통해 Python 생태계의 래퍼 비용을 걷어내고 순수한 하드웨어 성능을 끝까지 끌어올리는 시스템 엔지니어링의 위력을 확인했습니다.

• 한계점 (Limitations):
